## Proposed sequencing and PR boundaries

1. **#147 audit PR:** these artifacts and regenerated navigation maps only. Review occurrence classes and external evidence requests. No runtime changes.
2. **#149 compatibility PR:** prepare executable old/new URL handling and matching negative/positive fixtures; keep old identity active. Independent security review before implementation.
3. **#148 presentation/docs PR:** resolve prose/manual-review records and labels, retain compatibility contracts. Canonical link activation is prepared but timed to #150.
4. **#149 readiness PR/evidence:** integration results for the combined revision, external owner evidence, freeze/runbook and rollback review. #148 and #149 may develop concurrently but their combined state is a gate.
5. **#150 separately approved operation:** freeze, explicit owner go/no-go, rename, activate prepared URLs/remotes/integrations, identity and immediate service checks. Any small activation PR must already be reviewed.
6. **#151 verification PR:** fresh clone/PR CI, required checks, approved build/publish/deploy evidence, service/inference/backup checks, repeat inventory and retained-alias register. Do not remove aliases just to eliminate matches.

## Before / immediately after rename

Before: verify target-name availability; unchanged repository visibility/default branch; reviewed preparation merged; exact revisions/check evidence; known-good SHA and immutable image references; successful separately authorized scratch restore; external checklist; no in-flight conflicting work; automation freeze; named rollback owner and approved time window. Capture GitHub settings by identifiers/results only, never secret values. A repository rename does not require changing daemonhub.dev or its certificates.

Immediately after: confirm same repository ID/history at new URL; activate prepared repository identity selection; update approved clone remotes/callbacks/links; check required contexts/rules and access; run non-deploying CI first, then separately approved deployment and integration smoke checks. Resume automation only after owner acceptance. GitHub documents ordinary repository/Git redirects, but hosted-action references are an exception; do not use redirects as the verification strategy or reuse the old name. See [GitHub rename guidance](https://docs.github.com/en/repositories/creating-and-managing-repositories/renaming-a-repository).

## Rollback and stop conditions

Stop rollout for identity mismatch, unavailable required checks, broken deployment/inference/backup verification or unexpected data/mount changes. Keep working services and persistent mounts in place where safe. Restore approved code/configuration and known-good image digests; reverse external changes using an action ledger. Do not restore databases merely for a link failure. Host configuration needs its own rollback, not just a Git revert. Renaming back is another owner-approved operation, not an automatic action. Never delete volumes, rewrite history, remove backups, reuse the old repository name or rotate credentials as part of this audit.

The existing Docker socket exposure in OpenHands/status, broad Hermes reference-tree access, and optional non-RunPod inference remain architecture limitations. This epic must not worsen or misrepresent them. OIDC, rootless isolation, RunPod-only policy brokering and backup-era cryptographic erasure belong to separately scoped Haven work.
